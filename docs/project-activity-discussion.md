# Project Activity Feed and Project Discussion

This owner-requested increment adds two sections below the existing Overview progress, sections and deadlines. It preserves the development-phase ordering and the existing task, calendar, membership and notification features.

## Behavior

**Recent Activity** is the selected project's shared history, newest first. It includes the actor's own actions, even when their personal inbox has no notification. The first 20 entries are shown; **View More** fetches a larger prefix of older entries without a history/member cap. Reads use stable timestamp/ID ordering and keyset batching beyond an API page. Loading, empty and recoverable error states follow existing patterns. No read/unread state is added to activities.

Recorded actions are task creation, assignment/reassignment to a member, status/completion changes, deadline changes/removal, Task Comments and Project Discussion posts. A task created with an initial assignee produces **one creation activity** describing that assignment, while retaining the existing assignment notification. A transition to Done produces **one completion activity**, not an additional generic status activity. No-op saves and unrelated title/priority/description/step/resource edits create no entries. Unassignment keeps its existing notification behavior and adds no new activity type. Different relevant fields changed in one save represent separate activities. Administrative task writes without an authenticated actor continue to generate no user activity.

Activity displays the actor's minimal display-name snapshot, task-name snapshot where applicable, activity and timestamp. Task links use existing Task Details routes. Deleting a task preserves its activity snapshots and clears the task reference; the feed then shows **Task no longer available** instead of a broken link. A task deleted after a link was loaded is handled by the existing Task not found route. Project deletion cascades its activity history. Names are snapshots at the time of the action rather than continuously rewritten labels.

**Project Discussion** contains chronological plain-text comments for general project matters. Current members can post; only the author, while still a member, can delete a comment. There is no editing, threading, rich text, attachments, reactions, mentions or separate chat. Removing a member retains their historical posts/name snapshots for other current members, while revoking their own access. Deleting a discussion comment does not erase the historical fact that an activity occurred.

New discussion posts generate notifications to every other current project member through the existing Bell center. These have a project destination, `/projects/:projectId/overview#project-discussion`, instead of a task destination. Navigation focuses/scrolls the correct discussion section. Existing task links, read states, unread counts, recipient rules and deadline reminders remain in place. No popup, toast for incoming activity, realtime subscription, polling timer or external delivery service is introduced. New records appear on subsequent refreshes, following existing behavior.

## Database architecture and security

The new migration creates `project_activities` and `project_discussion_comments`. It changes only the existing notification trigger bodies necessary to call one private shared recorder; it does **not** add another set of task triggers. The recorder derives the authenticated actor and actual membership, inserts one project event and fans that event out to recipient notifications. `notifications.activity_id` links new deliveries to the shared event, with a unique recipient/event index preventing duplicate fanout. Deadline reminders remain separate and are not project activities.

The existing author/name preparation trigger is reused for Project Discussion because its fields and identity checks are identical. Column grants allow clients to insert only project ID/body, never author/name/time/ID. Discussion RLS requires current membership for reads/inserts and own authorship plus membership for deletion. Clients have no discussion UPDATE permission.

Activities are SELECT-only for current members. Client INSERT/UPDATE/DELETE and private recorder execution are denied. The recorder validates that any supplied task belongs to its project and any assignee belongs to that project. Trigger-only callers provide actual database mutation values, with no client-supplied actor or recipient lists. All definer functions have trusted postgres ownership, qualified relations and empty search paths. Existing membership, notification and Task Comment RLS policies are unchanged; removed members lose history/discussion access and their notifications are purged by the existing membership FK cascade.

Notifications gain the `discussion_added` kind and nullable task ID, constrained so only discussion notifications can omit a task. Existing task notifications, reminder uniqueness, read states and all existing data are preserved. New activity starts **when this migration is applied**; older per-user notifications cannot safely reconstruct missing actor-visible history and are not backfilled or relabeled as complete history.

## Exact manual Supabase setup

No migration or SQL test was executed remotely by the implementation agent.

1. In Dashboard select the intended **disposable** Supabase test project. Confirm the prior migrations are applied in order: `20261025000100_phase_2_foundation.sql`, `20261026000100_phase_3_integration.sql`, `20261026000200_calendar_busy_events.sql`, `20261026000300_comments_notifications.sql`. Do not rerun migrations already applied.
2. Open **SQL Editor → New query**, select **postgres**, paste the **entire** `supabase/migrations/20261027000100_project_activity_discussion.sql`, clear any text selection, review and Run once. It runs transactionally and commits the new feature structures/API schema reload. It replaces the two notification trigger bodies in the database through this new migration only; previous migration files remain unchanged. If it fails, save the first error and issue `ROLLBACK;` separately if the editor reports an aborted transaction. Do not run individual sections.
3. In a separate postgres query, paste/run the **entire** `supabase/tests/project_activity_discussion_authorization.sql`. It uses unique synthetic fixtures and ends with **ROLLBACK**. Never change rollback to commit. Accept the PASS result only if the whole file completes without errors. On failure retain the first error and run `ROLLBACK;` if needed before correcting/rerunning the complete file.
4. Refresh the local app. Through real authenticated sessions, create/assign/change a task, complete it and post a Task Comment. Check that the actor sees one shared activity and other appropriate members receive existing notifications. Check that a no-op/title-only save creates no history and that completion does not create both status and completion entries.
5. Post a Project Discussion comment. Confirm another member receives one Bell notification and that its link opens the correct project's discussion section. Delete an own post, attempt other-author deletion through the API, switch projects, use View More and reload to verify persistence. Remove a member via the existing leader flow and confirm their refreshed history/discussion/inbox access is revoked. Delete only clearly identified manual test projects through the leader UI after verification.

The SQL suite checks runtime roles without RLS bypass, a six-member project's fanout (no cap), real mutation-generated activities, one creation/completion per action, recipient linkage, no actor delivery, Task Comment compatibility, reminders without feed pollution, spoof/forge/edit attempts, own-only discussion deletion, cross-project isolation, removed-member access, deleted-task snapshots, cascades and helper grants/search paths. JWT claims are simulated by trusted SQL setup; this does not validate signed Google tokens or HTTP transport.
